# 快递履约数据分析

快递履约全链路分析：5 万运单、3 个区域仓、90 天数据、8 环节轨迹。从履约漏斗定位仓内作业、干线、派送与异常线路四类问题，量化优化优先级，并交付已上线的 Streamlit 分析看板。

项目完整覆盖数据分析五步流程：**数据采集 → 数据清洗 → 特征构建 → 输出结论 → 可视化**。

## 复现步骤

```bash
# 1. 采集：生成原始模拟数据（含约 3% 脏数据，需要 pandas + numpy）
python data/generate_data.py

# 2. 清洗：执行 5 条清洗规则，产出清洗后数据 + 清洗报告
python data/clean_data.py

# 3. 建库导入（MySQL 8，root 权限）
mysql -uroot -p < sql/01_schema.sql
mysql -uroot -p --local-infile=1 < sql/02_load_data.sql

# 4. 特征与指标：口径视图 + 指标 + 归因 + 漏斗
mysql -uroot -p -t < sql/03_analysis.sql

# 5. 启动看板（需要 streamlit + plotly + pymysql）
cd dashboard && streamlit run app.py
```

## 数据清洗（data/clean_data.py）

原始数据含约 3% 脏数据（由生成器注入，模拟真实系统落地质量）。5 条清洗规则，只清洗不修复、全程留痕：

| 规则 | 问题 | 动作 |
|---|---|---|
| R1 重复运单 | 同一运单号多条记录 | 保留首条，剔除重复 |
| R2 签收早于下单 | signed_at <= created_at | 剔除整单 |
| R3 重量异常 | 重量超出 [0.1, 100] kg | 剔除整单 |
| R4 轨迹时间倒挂 | 事件时间与业务链路顺序不一致 | 剔除整单 |
| R5 缺失关键事件 | 已签收单缺中间环节事件 | 剔除整单 |

清洗结果：运单 50,300 → 48,821（剔除 2.94%），轨迹事件 392,597 → 383,621。五类脏数据检出率 100%。明细见看板「数据质量」页与 `data/clean/cleaning_report.csv`。

## 特征构建（sql/03_analysis.sql 口径视图）

`v_waybill_stages` 将轨迹事件行转为"一单一行"的宽表，构建的特征：

- **环节时长特征（7 个）**：审单/出库/揽收/进始发仓/干线/分拣/派送（TIMESTAMPDIFF 小时）
- **时间特征**：派送日是否周末（周末口径按派送日而非下单日）、下单月份
- **统计特征**：全程时效、72h 超时标记、P80 分位（揽收时长右偏，P80 比均值更贴用户体感）
- **质量特征**：完美订单标记（准时 + 无异常）、慢单标记（派送 >12h）

## 核心结论

| 发现 | 证据 | 建议 |
|---|---|---|
| 华南仓仓内作业偏慢（漏斗瓶颈） | 出库 7.8h vs 其他仓 3.7h；揽收 12.8h vs 6.2h | 仓均全程 -10h（-17%） |
| 华东→华中干线 9 月起 +9h | 同期华中仓发同区域稳定 12h，排除目的地因素 | 核查 9/10 前后中转场变更 |
| 周末派送运力不足 | 工作日 3.8h vs 周末 7.7h，慢单占比差 40 倍 | 周末补员/众包运力 |
| 异常集中拒收，线路聚集 | 拒收 43.4%；华中→河南异常率 3.19% | TOP 线路前置验货 |

## 数据源与系统边界

本项目模拟两类系统的数据：

- **OMS**：运单、目的地区域、订单状态、异常类型
- **TMS**：全链路轨迹事件（下单→审单→出库→揽收→干线→派送→签收）、环节时效

规划扩展（当前未覆盖）：**WMS** 深度数据（库位、拣货波次、盘点差异）、**客服系统**（工单、NPS、退货申请）、**财务系统**（运费账单、对账差异）。

## AI 辅助分析方法论

- **数据构造**：模拟数据由 AI 辅助生成，但埋入的运营问题、脏数据类型与业务结构由人定义
- **口径设计**：所有口径决策（周末按派送日、时效仅取签收单、只清洗不修复、完美订单定义）为人工判断
- **归因逻辑**：横向对比、分位数选型、瓶颈定位思路为人工分析
- 原则：AI 放大分析效率，不替代分析思路
